# 第一次 SFT：从积木题到内存排查

这是一份学习记录：我们想弄明白模型如何从“积木题 + 参考计划”学习，也想弄清为什么一次很小的 LoRA 试运行让 Mac 使用了大量内存。这里记录本机实际观察，不把流程跑通当成模型已经掌握通用规划。

## 1. 这次做了什么？

Blocksworld 是一个文字版的积木世界。输入描述积木初始位置和目标，参考答案是一串动作，例如 `pickup(A)`、`stack(A, B)`。**SFT**（监督微调）用这些“问题 + 参考答案”教模型生成动作序列；**LoRA** 冻结大部分原模型参数，只训练额外的小矩阵。

两次试运行共同设置：Qwen2.5-0.5B-Instruct、Mac MPS、float32、512 道训练题、batch size 8、1 个 epoch（64 步）、学习率 0.0002、随机种子 0。原模型和数据来自本地；本次验证 loss 使用 64 条验证题，生成判分使用其中前 32 条。没有使用 test、6–7 块泛化集或 PlanBench 调参。

单轮样本通过 Qwen chat template 转成输入：题目作为上下文，assistant 的答案和结束符参与 loss；题目、补齐位置和结束符后的换行不参与 loss。mask 不会删除题目。**这份 mask 逻辑只针对当前单轮样本，不可直接假定适用于多轮工具轨迹。**

训练和验证脚本在 [`sft/`](../../sft/)：`data.py` 处理消息、token 和 mask；`train_lora.py` 组织训练；`eval_plans.py` 用模拟器检查输出；`mem_probe.py` 用于内存探针；`requirements.txt` 固定环境依赖。

## 2. 遇到了什么问题？

第一次训练时，我们现场观察到训练进程的 macOS **footprint** 约 76–77 GB、峰值约 80 GB；系统同时有约 29–31 GiB 的 swap（硬盘交换空间）在使用。footprint 是系统给进程的内存记账，swap 是整个系统的硬盘交换量；它们是不同指标，不能说这两项全部来自模型参数，或把其中一个直接加到另一个上。

进程中很大一部分记为图形加速相关内存。0.5B 模型用 float32 时，模型参数本身大约占 2 GB，但训练还要保存中间结果和临时分配；LoRA 减少可训练参数，不等于训练只需要保存 LoRA 矩阵。

## 3. 我们怎么检查？

先用短探针比较长度和缓存。下表取本机 `mem_probe.log` 中第 24 步结束后的 **MPS driver** 读数：这是 PyTorch 报告的 MPS 驱动管理内存，不等于系统进程 footprint，也不是整步瞬时峰值。

| 探针设置 | batch | 第 24 步 driver |
| --- | ---: | ---: |
| 每批补到本批最长 | 8 | 51.10 GiB |
| 每批固定补到 320 | 8 | 20.74 GiB |
| 固定补到 320，每步尝试清缓存 | 8 | 4.35 GiB |
| 每批补到本批最长 | 1 | 8.86 GiB |

这说明在这几次具体运行中，固定长度和清缓存都与较低的步骤结束读数相伴；它们提供了值得使用的工程线索，但不能单凭这些数据证明底层唯一原因，也不能证明不存在任何泄漏。`mem_probe.py` 的 `--generate` 在训练探针之后生成；原试运行在训练前也会生成，因此两者时序并非完全相同。探针中的 `峰值` 是 `ru_maxrss`，不能当作包含 MPS 图形分配的完整进程峰值。

当前探针和训练脚本中有将增长直接归因于缓存、或声称不是泄漏的简化注释；它们只是排查假设，不能作为本次实验已证实的结论，应以这里列出的观察和限制为准。

## 4. 修改后发生了什么？

第二次试运行将训练批次固定补齐到 320 token，并在相关阶段尝试清理 MPS 缓存；其他主要设置按本机结果记录保持一致。它不是只改变一个变量的消融实验。

| 指标 | 第一次：动态长度 | 第二次：固定长度 + 清缓存 |
| --- | ---: | ---: |
| 训练耗时 | 2726.6 秒 | 215.7 秒 |
| 总耗时（含评测与重新加载） | 2777.2 秒 | 300.5 秒 |
| 未微调的验证 loss | 0.8502 | 0.8502 |
| 第 64 步验证 loss | 0.1027 | 0.1060 |
| 生成格式正确 / 动作合法 / 最终成功 | 30 / 16 / 10 | 31 / 16 / 8 |
| 生成评测题数 | 32 | 32 |
| 重载后生成文字一致 | 32 / 32 | 32 / 32 |
| 同一输入的 logits 最大差 | 0 | 0 |

第二次结果记录了 64 个每步清缓存后的 MPS driver 读数，范围为 3.92–5.38 GiB；它**不是全程峰值**。结果文件没有逐步记录系统 swap，不能仅凭文件断言全程没有 swap。两次耗时也可能受到运行环境等因素影响，不能把提速完全归因于其中某一项修改。

32 道题中成功 10 道与 8 道，样本太小，不足以判定哪套设置的规划能力更好，也不能断言差异一定只是噪声。padding 改变了计算形状，浮点运算及训练时 dropout 的随机数使用等都可能影响结果；现有记录不能确定具体原因。格式正确不等于动作合法或目标完成，当前记录也没有单独证明模型总在正确结束符处停止。

## 5. 学到了什么，下一步是什么？

本次用真实代码走通了：**样本与 mask → 训练前对照 → LoRA 训练 → 验证 → 保存 adapter → 重新加载检查**。在这 32 道验证题上，未微调时成功 0 道，微调后两次分别成功 10 道和 8 道；这是小规模试运行的观察，不是独立测试集成绩或泛化能力证明。

下一步先逐行学习 SFT 代码，特别是样本如何变成模型输入、loss 如何产生、LoRA 更新哪些参数。完整训练前需要确定训练配置、验证频率和 checkpoint 选择方式，并给每次运行使用独立输出目录，避免覆盖已有成果。

**安全提醒：**目前 `sft/train_lora.py` 使用固定输出目录 `outputs/sft/qwen0.5b-lora-trial/`；直接重新运行会覆盖已有 adapter 和 `results.json`，中途失败也可能造成记录与 adapter 不匹配。请先保护已有结果并改用不冲突的输出路径。模型默认路径指向另一项目的本地目录；`QWEN_0_5B` 可用于指定其他本地模型目录。训练、测试数据和模型文件都没有包含在 Git 仓库中。
